# Additional Gallery issues — remediation proposals

This addendum extends the cross-project catalog for other open Gallery issues recorded in SER-12. These are proposals, not changes to Gallery's source repository. Verify current status before taking action; issues may have changed since this snapshot.

## [#1279 — Gemma E2B retraining, knowledge freshness and routing](https://github.com/google-ai-edge/gallery/issues/1279)
**Recommendation: split the request into separate problems rather than promise a retrain.** A stale knowledge cutoff belongs to the model/retrieval strategy; zero-skill fallback and incorrect skill selection belong to Gallery's agent router; GPU-vs-CPU calculation differences belong to backend/model evaluation and are tracked separately in #1282. A Gallery code change cannot by itself update the weights of a model published by Google. First fix and test routing: when there are no enabled/matching skills, answer through base chat. For facts that must be current, use a bounded retrieval/fetch path with visible sources or use a newer officially published model revision. Fine-tuning/QAT should be considered only by the model owner with a licensed dataset and held-out evaluation. Quantization-aware training is not a substitute for isolating a backend discrepancy. Tests: date-sensitive questions with source retrieval, zero/irrelevant skill cases, arithmetic on CPU/GPU, and model-version metadata.

## [#1282 — Gemma E2B code/math result differs on GPU and CPU](https://github.com/google-ai-edge/gallery/issues/1282)
**Reported: same prompt reportedly gives different count results on GPU vs CPU.** Isolate inference from execution before deciding this is a code-runner fault. Fix generation controls (model file/revision, seed where honored, sampler, temperature, prompt and app build); capture raw model output/tool arguments and the actual code-runner input/output for each backend. If raw output differs, investigate backend numerics, quantization and determinism; if identical code reaches the runner but results differ, inspect the runner/bridge. For simple arithmetic/counting, prefer deterministic local computation and treat model-written code as untrusted input, not proof of correct execution. Add a fixed corpus, CPU/GPU repeated runs, raw trace capture and a regression demonstrating the first layer where results diverge. Do not claim QAT is the fix without isolating the layer.

## [#1304 — optional self-verification mode](https://github.com/google-ai-edge/gallery/issues/1304)
Implement as an opt-in experiment, not an always-on second model call. Use deterministic checkers when available for arithmetic, structured output and code; use a short second pass only for checks without a reliable programmatic oracle. For unsupported facts, report uncertainty or retrieve evidence rather than letting the model approve itself. Skip verification on low-risk/simple prompts using a transparent policy and cap extra tokens/time. Benchmark against normal inference on Spanish instruction following, arithmetic, insufficient-information questions, contradictions and multi-turn consistency. Measure correctness, false confidence, false corrections, latency, memory and energy. Release only if held-out tests demonstrate net benefit.

## [#1305 — reproducible benchmark summaries](https://github.com/google-ai-edge/gallery/issues/1305) and [#1285 — existing benchmark sample](https://github.com/google-ai-edge/gallery/issues/1285)
Record individual runs and export JSON/CSV with run timestamps, model and bundle hash/revision, device/OS, app/runtime version, accelerator, sampler/generation config, input/output token counts, cold-start init, steady-state init, time to first token, prefill and decode throughput. Summarize with median and a variability metric (IQR or standard deviation); optionally add p90/p95 when sample count supports it. Keep cold/warm measurements separate and label failures/timeouts. #1285 is historical context, not proof the feature is implemented. Tests: deterministic fixture data, repeated-run aggregation, missing-field handling, export round trip and measurement overhead.

## [#1306 — controlled CPU/GPU comparison](https://github.com/google-ai-edge/gallery/issues/1306)
Build the comparison on #1305's measurement schema. Use the same model artifact/revision, prompt set, generation settings and context limit. Alternate or randomize CPU/GPU run order to reduce thermal/order bias, include warmups, repeat enough trials to report variability, and capture battery/thermal state where supported. Report performance and output quality separately; faster output is not necessarily better. Flag unsupported backend/model combinations instead of comparing different model variants. Test that the two arms use identical settings and that output divergence is reported without assuming which backend is correct.

## [#1308 — `.gitignore` hygiene and secret safety](https://github.com/google-ai-edge/gallery/issues/1308)
Inspect the actual tracked file and repository status before editing. Add precise ignore rules for local signing credentials, `.env`/machine-local secrets, build outputs and generated `.aab` artifacts where those files are not intended to be versioned; remove redundant rules only when behavior is unchanged. Do not blanket-ignore source/config files or required model/test fixtures. Check whether sensitive files are already tracked: `.gitignore` does not untrack files or clean history. If a real credential entered history, revoke/rotate it first, then follow the repository's approved history-rewrite policy. Tests: `git check-ignore`, status of expected build artifacts, and an audit that required files still appear in `git status`.

## [#1310 — broad UI/UX improvements](https://github.com/google-ai-edge/gallery/issues/1310)
This is a bundle of features, not one defect. Split it into small product decisions and prioritize based on observed user friction. A practical first milestone is a clearer home/model card showing verified model/backend compatibility and a consistent benchmark summary; theme customization, sidebar, multi-panel layouts, thermal dashboard and keyboard shortcuts are separate items. Use existing navigation/design patterns, accessibility checks and screen-size tests. Do not claim live temperature, accelerator load or energy values unless the platform exposes a reliable API on that device.

## [#1311 — evaluating/importing fine-tuned Gemma/E2B models](https://github.com/google-ai-edge/gallery/issues/1311)
Gallery should not claim to train the model in-app. Scope the proposal to importing already-converted, runtime-compatible artifacts with a manifest (base model/revision, fine-tuning method, adapter merge status, quantization, dataset provenance/license and task). If LoRA/adapters are unsupported in the runtime, document the conversion route instead of suggesting arbitrary checkpoints will load. Add an apples-to-apples base-vs-fine-tuned benchmark and task evaluation with held-out data; track overfitting and regression on general tasks. Any retraining/fine-tuning itself belongs in a separately licensed model-training pipeline and must publish evaluation evidence.

## [#1313 — accelerator capability panel](https://github.com/google-ai-edge/gallery/issues/1313)
Build the panel from capability facts available from the runtime, bundle manifest and device API. Clearly distinguish **supported/verified**, **unsupported**, and **unknown**. Show operator/backend support and quantization/model compatibility only when checked; show empirical performance ranges only from matched device/model benchmark data, not generic guesses. Thermal telemetry should be labelled with what the OS actually reports. Test missing metadata, different device families, unsupported delegates and agreement between the panel and engine-load results.

## [#1314 — custom dataset evaluation](https://github.com/google-ai-edge/gallery/issues/1314)
Start with a bounded local JSONL manifest for text tasks and optional image references, validated schema, size limits, cancellation and resumable results. Keep dataset contents on-device by default, clearly warn before export, and never collect private prompts by telemetry implicitly. Each run should record model revision, backend and generation config; support optional reference answers/metrics only where meaningful, plus a manual review path for open-ended generation. For multimodal evaluation validate file type/size and preserve offline operation. Test invalid rows, partial failures, sensitive data handling and export/delete behavior.

## [#1315 — thermal profiling during benchmarks](https://github.com/google-ai-edge/gallery/issues/1315)
Use supported Android thermal-status/temperature APIs where available and report their actual semantics. Do not claim a GPU/CPU-specific temperature if the device exposes only skin/battery or coarse thermal status; show “not available” otherwise. Correlate the time series with benchmark runs, throughput and throttling events, and make sensor polling low overhead. Test unsupported sensors, permission/API variance, missing values and long runs; label device-specific metrics accurately.

## [#1316 — prompt presets](https://github.com/google-ai-edge/gallery/issues/1316)
Implement editable, localized presets for summarization, Q&A, code, translation and image captioning only when the loaded model supports the modality. Store a versioned preset list with explicit placeholders and safe substitution; don't concatenate user input into template/control syntax. Let users preview/edit before sending and keep custom prompts separate from defaults. Tests: localization, empty/long input, placeholder escaping, model/modality compatibility and accessibility.
